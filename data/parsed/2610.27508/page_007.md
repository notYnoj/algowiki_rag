<tbc>the pipeline, keeping dense distance computation on the matrix engine and scalar selection work off the critical path.

**All-centroid routing as a dense scan.** One way to reduce coarse-search cost is to add a secondary approximate router, but that introduces query-dependent control flow and another source of routing error. KatoANN instead scores every centroid for every query in the batch. This is feasible because the centroid table is small compared with the database, and it has the same dense shape as an inverted list that every query probes. At build time, KatoANN quantizes centroids into SQ16 and stores their high and low byte planes in the same VNNI-order layout as database codes. At query time, the coarse search becomes a dense batched byte-split scan over all centroids, followed by a per-query partial selection of the nearest nprobe centroids. This introduces no additional routing loss from an approximate router, because every centroid is scored under the same SQ16 distance model used by the fine scan. The cost is flat in nprobe, so the same routing path supports both moderate and high recall targets.

**Keeping selection off the critical path.** Once distance computation becomes cheap, a scalar heap can dominate. KatoANN uses two selection paths because the best way to avoid heap overhead depends on the probe regime. At high probe counts, each query sees many candidates, so its current _K_-th-best distance \(\tau_K\) tightens quickly. KatoANN uses threshold-guarded selection, in which a SIMD compare rejects distances larger than \(\tau_K\) before they reach the heap. The compare runs on vector units while AMX continues producing later distance tiles, so most candidates are discarded without stalling the matrix engine.

At low probe counts, the candidate pool is smaller and \(\tau_K\) remains loose. In this regime, threshold rejection is less effective because many distances still pass the guard. KatoANN instead keeps a small insertion-sorted array of the best \(S=R\cdot K\) candidates per cluster and merges those local lists across clusters. This local selection is exact for the global top-_S_, because a query’s global top-_S_ must be contained in the union of the per-cluster top-_S_ sets. The local path replaces data-dependent heap updates with short inregister insertions and switches back to threshold guarding when the probe count is large.

## 3.5 Dimension Cascade

The rank-then-refine cascade reduces precision cost, but on high-dimensional embeddings the ranking pass can still dominate because it touches every probed candidate. Even a one-stream high-byte pass becomes expensive when each candidate has hundreds to thousands of coordinates. KatoANN therefore adds a dimension cascade. It ranks all candidates using only a short prefix, then refines the survivors using the full vector.

A naive prefix would discard useful signal arbitrarily. At build time, KatoANN applies an orthogonal rotation that concentrates variance into leading coordinates while preserving full-dimensional distances before quantization. The ranking pass then uses only the first _d_<sub>0</sub> dimensions of the high-byte plane. This reduces the work paid for every candidate, which is the dominant cost of the ranking stage. The refinement pass still uses all _d_ dimensions of the SQ16 code, so the prefix affects only which candidates reach refinement, not the final distance used for high-recall ranking.

The prefix length _d_<sub>0</sub> and survivor factor _R_ are calibrated together. A smaller prefix reduces ranking cost but may require more survivors because the prefix ordering is less sharp. A larger prefix costs more per candidate but gives a more reliable ordering and can reduce the survivor set. The plain cascade is the special case _d_<sub>0</sub>=_d_, where no dimensions are dropped and the ranking pass uses the full high- byte vector. The calibration selects this case automatically when the data does not compress well, and selects a shorter prefix when the variance concentrates in the leading coordinates. The result is a cascade that becomes cheap in both bits and dimensions for the candidates seen by the ranking pass, while the final refinement remains full-dimensional.

## 3.6 Discussion

**Hardware portability.** The implementation in this paper targets Intel AMX, but the structure is more general. The design requires a low-precision matrix engine, a way to feed it dense tiles, and enough accumulator precision to recombine byte-split partial products safely. Such engines are becoming a standard CPU feature rather than an Intel-only one. Arm ships a comparable unit today through the Scalable Matrix Extension (SME2) of Armv9 CPUs. We therefore expect the byte-split decomposition and the cascade to apply on these engines, subject to their operand types and accumulator widths.

**Scaling beyond a single server.** KatoANN is a per-shard, in-memory ANN search system, but larger data can be partitioned across multiple servers. This distributed setting preserves two key properties of the design. First, KatoANN’s throughput advantage comes from reducing the cost of each distance comparison, so it does not depend on the total collection size. We therefore expect the per-shard advantage to remain as more shards are added. Second, Eq. 2 becomes a placement constraint. A shard remains compute-bound only when enough concurrent queries reuse its resident lists. The distributed front end should therefore route queries in a way that preserves the effective batch size seen by each shard, and cluster placement should keep frequently co-probed clusters on the same shard to maintain list reuse.
