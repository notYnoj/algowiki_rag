# PrairieFire: Igniting High-Throughput Updates in Large-Scale Approximate Nearest Neighbor Search

### ABSTRACT

Arrays of modern NVMe SSDs are approaching memory in terms of bandwidth in a single server while offering much lower cost per gigabyte. Hence, approximate nearest neighbor search (ANNS) for billion-scale vectors in applications such as recommendation, search, and retrieval-augmented generation increasingly runs on SSD-based systems. Unfortunately, due to the limited update throughput of existing SSD-based solutions, the indexed corpus cannot keep pace with continuous modifications to data and embedding models, thus hindering broader deployment across more scenarios and larger scales.

The bottleneck lies in CPU-intensive update paths, where foreground insertions incur frequent SSD accesses and background reassignments repeatedly relocate each vector, making high update throughput difficult to achieve even by exhausting available hardware. In this paper, using buffered updates and batched local rebuilds, we develop PrairieFire with cascaded adjustments, concurrency control, and CPU-GPU-SSD cooperation. These co-designs avoid frequent SSD accesses in foreground updates and heavy background reassignments, achieving high update throughput while maintaining excellent search performance.

Evaluations show that, compared with state-of-the-art systems, PrairieFire can sustain ∼3-35\(\times\) update throughput while maintaining ∼3-5\(\times\) search throughput simultaneously. It also achieves ∼1.5-8.7\(\times\) cost efficiency. PrairieFire has been deployed in RedNote’s production environments for two months, improving business metrics (e.g., click-through rate) by higher freshness without frequent index rebuilds.

### 1 INTRODUCTION

Approximate nearest neighbor search (ANNS) over embedding vectors underpins online services such as recommendation, search engines, advertising, and retrieval-augmented generation [34, 35, 36, 38, 39]. To reduce storage cost over billions of vectors, recent systems try to place raw vectors as cluster lists or as graph nodes with neighboring edges from DRAM onto NVMe SSDs [17, 23, 29, 57, 62]. The corpus of vectors, however, is anything but static. In upstream applications, items are continuously created and retired, and the underlying embedding models are continuously adjusted and synchronized at an hourly or finer cadence to track shifting user behavior for better business outcomes [38, 42]. A practical ANNS service must therefore find top-_k_ results against the latest valid data while continuously absorbing a stream of inserts and

deletes arising from both dynamic items [24, 64] and continual learning of embedding models [22, 69].

To support updates, based on existing static ANNS [17, 57], two notable solutions have been proposed (i.e., OdinANN [24] and SPFresh [64]). OdinANN follows the graph structure [57] and introduces direct modifications to avoid the inefficiency of periodic merging (e.g., 1.5-2\(\times\) search latency and ∼3\(\times\) peak memory usage during merging [55, 67]). SPFresh adopts a partition-based structure, which routes vectors to partitions through an in-memory centroid index and maintains partitions’ lists on SSDs. To address the degraded index quality under continuous updates, SPFresh introduces a local rebuild mechanism that splits or merges partitions and reassigns vectors to their nearest partitions.

However, when extending SSD-based ANNS to broader largescale scenarios, their update performance becomes a limitation. Recent industrial practice points out that, to track user behavior in real time, the continual learning [22, 38, 42, 69] of embedding models calls for high-throughput updates. For a 0.1B-scale index in recommendation systems, maintaining freshness demands an update throughput of up to 30K queries per second (QPS) to match [29]. This requirement is comparable to the search throughput of online services, making updates the other first-class performance target. But even if we deploy an SSD array with _\>_100GB/s bandwidth and exhaust all 64 CPU cores on update-only operations, OdinANN and SPFresh can only sustain about 6% to 40% of the target.

Graph-based OdinANN achieves only 2-3 KQPS because each update searches ∼100 neighbors before modifying links, incurring ∼4- 7 ms due to inherent multi-hop SSD accesses [29, 30, 62]. Partition- based SPFresh routes inserts through in-memory centroids (_\<_1 ms), but rewriting SSD posting lists per insertion in foreground still incurs unacceptable CPU consumptions. Background per-vector relocations after splits or merges require extra CPU cores to deal with centroid locations and partition updates. Even with 64 CPU cores for update-only requests, it can only reach ∼12 KQPS.

Hence, we propose to use buffered updates and batched reclustering for rebuilds, instead of immediate flushes and asynchronous reassignments in SPFresh. First, buffered updates can amortize the overhead of foreground SSD round trips, where multiple updates to the same cluster are accumulated in memory and flushed to SSD as a batch. Second, we can recluster an imbalanced region, replacing the steady drip of per-vector reassignments with a single batch local rebuild. However, it is non-trivial to apply these ideas.
