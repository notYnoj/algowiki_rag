The third implementation represents our new _in-place Mergesort_, as depicted in Algorithm 5, which--besides logarithmic stack space for the recursions--does not need additional memory.

The _qsort()_ reference implementation generally uses the _Quicksort_ algorithm, originally developed by Tony Hoare in 1959. However, it is highly optimized and uses _insertion sort_, i.e., another sorting algorithm, for a small number of elements below a certain threshold. Besides that, it implements a better pivot selection strategy and other optimizations, such as all-lining, a non-recursive stack, cache-friendly data layouts and streamlined data accesses. So while we can expect better performance, it is important to remember that _Quicksort_ implementations and, hence, also _qsort()_ are not stable. As such, the C standard restricts its use and states that if two keys compare as equal, their order in the sorted array is undefined.

On the other hand, both shown _Mergesort_ implementations are stable and straightforward implementations without any special optimizations. Due to the threshold-selected algorithm choice in the reference implementation, the buffered _Mergesort_ is around 50 to 100% slower than _qsort()_ for small numbers of elements and only around 26 to 40% for large numbers of elements. This is quite good, considering that many of the optimizations applied to _qsort()_ can also be applied to both _Mergesort_ implementations. For example, we can make the new _Merge_ algorithm _memory-adaptive_ by setting some threshold, i.e., the amount of additional memory that we are willing to spend in exchange for some performance gains, and switching to a different sorting algorithm whenever it encounters a smaller array, e.g., during recursion. Nevertheless, any such optimizations regarding an actual implementation are outside the scope of this paper, and reintroducing additional memory for improved speed would essentially revoke the quality characteristic of working _in place_.

Ignoring any optimizations, a fairer comparison of the traditional buffered _Mergesort_ and the new _in-place_ variant should reveal the actual performance overhead needed in exchange for reducing the additional memory footprint from O(_n_) down to O(log_n_). While there is a factor of O(log_n_) for the theoretical performance difference, the new _in-place Mergesort_ actually becomes only a factor between 2.0 and 3.1 slower than the traditional _Mergesort_ implementation, or a factor of 2.6 to 4.0 slower than the optimized _Quicksort_. Although this is expected theoretically for the number of comparisons executed (see Section 3.1), this is a rather positive surprise for these practical measurements due to the still necessary array rotations (see Section 2.1). A straightforward analysis with the statistical profiler _GNU gprof_ determined that, e.g., in a sorting run with 62 million elements, 10.9 seconds of the _in-place merge_ were spent in the co-ranking, while 13.3 seconds were spent in the array rotation. Increasing this problem size by a factor of 10 increases these numbers to 121.6 seconds (\(\times\) 11.2) for the co-ranking and 176.7 seconds (\(\times\) 13.3) for the array rotation. A curve fitting revealed a constant factor of 6.1 (\(\pm 0.5\)) for the O(_n_log_n_) co-ranking part and a constant factor of 0.25 (\(\pm 0.05\)) for the O(_n_log<sup>2</sup>_n_) array rotation part. While the actual work due to the array rotations is a factor of O(log_n_) worse than for the number of comparisons, the practical constant is much smaller--the actual timings are almost on par (43% vs. 57%).
