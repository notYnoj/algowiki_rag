## 3 In-place Mergesort

The traditional top-down implementation of _Mergesort_ uses recursion, as shown in Algorithm 3. The problematic part lies within its _Merge_ routine, drafted in Algorithm 4, which typically allocates a temporary buffer of the same size as the original input array, merges two array halves therein, and copies the results back into the input array. This strategy obviously requires O(_n_) additional memory and thus does not work _in place_. It should be noted that the array halves used in _Mergesort_ are always direct neighbors, i.e., the first array ends where the second array starts. This property will help us later create an _in-place_ variant of _Merge_. For this reason, _Merge_() can either call _Merge_buffered(_A,mid,n-mid_) or _Merge_inplace(_A,mid,n-mid_). Consequently, an _in-place Merge_ will directly lead to an _in-place Mergesort_.

Before focusing on the actual _in-place_ variant of _Merge_ and accordingly _Mergesort_, we have to clarify when an algorithm can be called _in-place_. If it needs no additional memory but also only a constant amount, it is called _strictly in-place_. But since such an O(1) requirement is often too restrictive and would exclude any algorithm with a recursive nature, which would already need an O(log_n_) additional space for the recursion stack itself, the following definition is generally approved and can, e.g., be found in [13] (Def. 11.6 on page 215):

\(\blacktriangleright\) **Definition 2.** _An algorithm for an input length n is called_ in-place _if it uses_ O((log_n)<sup>c</sup>_) _additional space (where c is a constant)._
