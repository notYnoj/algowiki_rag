First and foremost, the signature feature of inverted indexes is that a sparse query vector only needs to touch the posting lists associated with its non-zero vector components. For sufficiently sparse vectors, this drastically reduces the search space. Standard graph-based indexes discard this structure. GRIP explicitly ports this structural advantage of the inverted index into graph search via a technique we call _term-based entry point seeding_, which precomputes, for every vocabulary term, the documents with the largest weight on that term, and initializes the graph search from the documents listed under the query’s highest-impact terms. Better entry point selection for graph search is a well-studied problem in the vector database literature, both for dense retrieval [30] and by seeding graph traversal with the results of a separate lexical retrieval stage [19]. GRIP differs from prior work in using the sparse embeddings themselves as the entry point selection mechanism, which requires no additional retrieval system and almost no additional work at query time, making graph search \(1.95-2.59\times\) faster on its own in our experimental evaluations.

Secondly, we further accelerate GRIP via an optimization we call _approximate routing via sparse sketching_ that is also inspired by inverted index designs for LSR. Learned sparse embeddings exhibit _concentration of importance_ [5]: a small number of components carry most of each vector’s weight. We exploit this property by sketching each document as its _R_ largest-magnitude components and running the graph traversal entirely on these sketches, then reranking the final candidates against the full vectors. Because learned sparse weights are non-negative, a sketched score is always a lower bound on the exact score, so only the navigation of the graph is approximate, and the returned results are scored exactly. This sketching is complementary to quantizing the stored weights, which we also apply; sketching reduces how many components each distance computation touches, while quantization reduces the cost of each one.

Our final key optimization is not related to accelerating the query time of GRIP but rather the graph index construction. Traditionally, graph-based vector search indexes are constructed by calling the query function as a subroutine, inserting each new node by searching for its nearest neighbors among the documents already in the graph and adding edges according to a set of heuristics. As we show in this paper, sparse vectors are ill-suited to this search-based construction approach: while graphs over dense embeddings typically see diminishing returns beyond a construction beam width (ef\_construction) of roughly 200 [14], we observe that HNSW graphs over learned sparse embeddings require a beam width of 2000 to achieve competitive search quality (when combined with our other aforementioned optimizations). However, this increase blows up the graph construction time by roughly an order of magnitude, and on the MS MARCO v2 dataset, we estimate that we would require several days to build the graph. To solve this problem, we take inspiration from PiPNN [31], a recently proposed index construction algorithm that replaces the incremental search-based procedure of prior systems with vector partitioning and hashing. PiPNN’s partitioning step, which assigns points to randomly sampled leaders, closely mirrors the shallow _k_-means clustering that Seismic uses to organize its posting lists, and we find that it partitions learned sparse vectors effectively.

However, we cannot apply PiPNN to learned sparse vectors out- of-the-box because PiPNN computes nearest neighbors within each partition using dense matrix multiplication, which is wasteful for sparse vectors spanning tens of thousands of dimensions. Again taking inspiration from inverted index designs for LSR, we instead compute these inner products from a small inverted index built over each partition. We apply this approach to develop a sparse variant of PiPNN we call _sparse partition-based graph construction_, followed by a single refinement pass in which each document searches the finished graph from its own term seeds. This reduces the time to construct a GRIP graph from 5.5 hours (with HNSW) to 47 minutes on the 8.8M MS MARCO v1 collection with SPLADE-CoCondenser embeddings. While we show that GRIP’s sparse PiPNN graph is somewhat weaker than an HNSW graph under standard search, the order-of-magnitude improvement in construction time allows us to build the graph for MS MARCO v2 in hours (7.3 hours) as opposed to days.

In addition to improving our scientific understanding of index design for learned sparse retrieval, enabling graph-based indexes to be more efficient for sparse vector workloads also has important practical implications. Many modern retrieval systems now deploy so-called _hybrid_ search strategies where dense and sparse retrieval are combined to produce a final list of results. Since such systems already typically deploy graph-based indexes for dense retrieval, they may be able to consolidate and simplify their infrastructure by reusing the same components for sparse search as opposed to having to maintain separate inverted index logic. Moreover, the popularity of graph-based indexes has led to a mature ecosystem of high-performance libraries and remains an active area of research. Thus, efficient graph-based search for LSR can enable the sparse retrieval community to also take advantage of these ongoing developments.

In summary, this paper makes the following contributions:

\(\bullet\) **End-to-End System:** We challenge the conventional wisdom that graph-based indexes for sparse vector similarity search are uncompetitive with inverted indexes at practically relevant document collection sizes. We support this claim by presenting GRIP, a new system for graph-based learned sparse retrieval that achieves substantial performance improvements over standard graph-based search designed for dense retrieval via three algorithmic techniques which we highlight further below. These results call into question the default choice of inverted indexes for deploying learned sparse retrieval.<tbc>
