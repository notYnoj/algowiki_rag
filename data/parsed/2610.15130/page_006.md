<tbc>same Merge\_Size as the unmodified baseline. Partitioning is therefore invisible to M_<sub>c</sub>_ as a matter of code path, which is why the bound carries. We check that construction rather than infer it: with a single predicate and tenant the full C2+C3 prototype reproduces baseline post-merge recall@10 to \(\delta=0.000\) at three successive checkpoints (99.286/99.145/99.018, brute- force _K_=100 ground truth), with the ceiling-disabled, ceiling- never-firing, and FIFO legs byte-identical.

## B. C2: a filter-aware, tenant-aware staging cache

FreshDiskANN stages pending inserts in two in-memory buffers double-buffered against the disk merge. We re-key each buffer to a hash map over _partitions_ (_predicate,tenant_) and consult it on the query path, routing a query to its own partition and label-post-filtering disk results. The cache therefore serves freshly-inserted, same-tenant points immediately, which is what makes filtering on the query path viable and is essential for filtered queries, since disabling the query-path keying costs 72-86 pp of per-label recall@10 at live cache occupancy (93.8/78.9/81.1 keyed vs. 7.8/7.3/7.6 unkeyed, at comparable p99, with _identical_ probed staging occupancy in both legs so the staging state is held fixed). This ablation toggles more than a cache-probe comparison. A single query key drives both the cache probe and the disk post-filter, so the unkeyed leg is not a filter-blind cache alongside a correct disk path, since it pins every query’s key to one default partition, which simultaneously blinds the cache probe and points the disk post-filter at the wrong label for every tenant but one. The residual 7.5% is accordingly close to arithmetic, approximately the one correctly-keyed tenant’s share of the query mix times its recall. What the ablation establishes is that _the query-path keying as a whole_ is central; it does not measure a cache-probe-only lift. Isolating the probe would require holding the disk post-filter on the true label while blinding only the cache, which the current knobs do not expose; the tighter comparator (a filter-blind cache that post-filters its own contents) is therefore not measured. The cache changes only _what is staged and how queries route_, not the merge cadence; at a merge, all selected partitions are folded into _one_ combined in-memory index and drained as a _single_ merge of size _c_ (the combined-index single-merge drain), identical in topology to the baseline (merge-order parity \(\delta=0.000\)). This is what lets the bound carry to the prototype unchanged. Unlike read-side or filter-blind caches over vector indexes (Ubis, MicroNN, QVCache), ours is jointly filter and tenant-keyed, on the query path, and is the exact structure the theorem binds.

## C. C3: an SLA-aware, select-not-resize scheduler

The scheduler **never re-sizes a merge**; every fired merge is one combined fixed-size-_c_ drain (bound-safe by construction, §IV-A), and it wins by _selecting which pending work fills each merge and when_. The rule follows from Theorem 3, by which re-sizing is not a recall lever in the first place, so there is nothing to gain, and from holding the merge at the baseline’s shape, which keeps the bound applicable without re- deriving it per configuration. An implementation observation that draining _N_ partitions as _N_ separate merges reads much<tbc>

<tbc>worse (84.9/76.4/70.1) than the one-combined-merge design is _not_ used as evidence, since it holds nothing fixed, and the design rule rests on the two reasons above.

It orders background repair by a composite key

\(\kappa(w,t)=\alpha_1\mathrm{stale}(w,t)+\alpha_2\widehat{\Delta R}(w)+\alpha_3\mathrm{SLA}(w)+\alpha_4\mathrm{mig}(w),\) (9)

over staleness, predicted recall impact, tightest tenant SLA, and migration cost, each min-max normalized across the pending set at drain time. _Exactly one of these terms is exercised in every measurement we report_. The \(\widehat{\Delta R}\) term is implemented as an occupancy proxy behind a default-off flag and is disabled (\(\alpha_2=0\)) throughout, and no result depends on it. The migration term is identically zero in this prototype. The SLA term is inert whenever tenants share one SLO, since a term with a single distinct value normalizes to zero, and our churn legs additionally set \(\alpha_3=0\) so that ceiling enforcement is the only variable. So \(\kappa\) reduces to staleness ordering (oldest-first) in all reported runs; deferred units reload as the oldest across the driver’s per-merge restart and drain first. The four-term form is the interface the scheduler exposes, not a mechanism this paper validates; the measured win below comes from the ceiling.

On top of \(\kappa\), a **per-tenant max-taleness ceiling** \(S_\tau\) forcedrains a tenant whose staleness has reached \(S_\tau\). This is a _prioritization with a cadence-bounded overshoot_, and the distinction matters for Theorem 8. The built scheduler tests ceilings only at a merge trigger, with no early-merge on crossing, so a tenant that crosses \(S_\tau\) mid-window stays stale until the next trigger. The guarantee we actually deliver is

\(N_\tau^\mathrm{stale}\le\lambda_\mathrm{ins}^{(\tau)}\big(S_\tau+W\big),\) (10)

where _W_ is the trigger window (the high-water mark). The theorem’s \(\lambda_\mathrm{ins}^{(\tau)}S_\tau\) cap is thus the \(W\rightarrow 0\) idealization; the prototype attains it up to one window, and we set \(W=S_\tau^\mathrm{min}\) to make that overshoot as small as the design admits without an early-merge mechanism. The effect is directly visible in our runs, where a tight tenant’s measured staleness reaches 1900 against a 1000 ceiling before the force-drain resets it, and in an earlier configuration (even with _W_ set equal to \(S_\tau\), the tightest the built cadence allows) the tight tier was still violated at one checkpoint on _both_ legs for exactly this reason. Closing the gap would need an early-merge trigger. FIFO/threshold-triggered compaction (all prior streaming systems) has no per-tenant lever at all; §V-E shows the ceiling is what drives tight-tenant violations to zero under churn.

## D. Deletes and tenancy migration

Deletes are tombstoned in the staging partitions and evicted at the combined merge; a tenancy migration is a delete in \(\tau\) plus an insert in \(\tau'\). We extend the drain to evict tombstones from _every_ partition (not only a default one), verified to conserve points (zero silently-dropped) and to leave deleted ids absent from post-merge results while survivors remain. This is what admits the deletes/migration term of Theorem 8; the term’s precise floor contribution \(g_0^\mathrm{del}\) is not characterized here.
