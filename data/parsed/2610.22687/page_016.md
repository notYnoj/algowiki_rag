## E. Declaration and surface

The `core` module is by construction completely unambiguous: all types are fully specified and there are on purpose no implicit conversions (e.g. "this string actually means a dictionary key"). This makes it relatively light and maintainable: there are no such conveniences to maintain or extend in the `core` module.

However, declaring, manipulating, and executing the graph in many cases requires referring to nodes and variables. Furthermore, while declaring the graph, one should be able to give explicit values (a tolerance, initial values, or optimisation bounds) or additional information (e.g. units, runtime, shapes) that have no place in the base graph. In principle, the `core` module supports these use-cases, but it can be inconvenient to always use the `cottax`-native types or keep a parallel structure with all additional information. To keep the `core` module light, extensible, and fast, these conveniences are instead in the `surface` and `declaration` consumers. They make this significantly easier by providing a way to implicitly convert arguments (e.g. a "function means its outputs", or "a string refers to getting that attribute") and by providing a parallel data structure for the additional information. Additional surface-level methods (e.g. an architecture referring to a particular node also wants to have a convenient method to refer to it) can register their additional functions.

A workflow can combine defaults and particular consumers into one convenient surface. Here, we show two simple examples of how such a convenience surface works, and for further details, we refer to the `cottax` documentation.

In Figure 12, the extended Sellar problem with an implicit discipline (of Section IIIE) is shown in the `cottax` interfaces in two different ways. Functions can be decorated, giving just their output and reading the inputs from the signature, or can be converted to a `cottax` function with possibly explicit paths into some kind of data structure. The flat namespace is convenient for scripting and quick tests, while the explicit paths are useful to construct hierarchical model trees and data structures. This can even be performed programmatically to arrive at a similar subsystem decomposition as performed in e.g. OpenMDAO. Values in the graph declaration are converted to external inputs with an associated value (e.g. the bounds). The total declaration can be run in a simple manner, see Figure 13.

A similar interface is available for ODEs (using e.g. `flat.rate`); again, see the `cottax` documentation for further details.
