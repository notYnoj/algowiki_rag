<tbc>Our second contribution is the execution of this extended graph using JAX [30]: the entire `cottax` graph, including its nested solves and its orchestration, becomes one transformable JAX function, enabling efficient execution, differentiation, and batching. The JAX just-in-time compilation then removes the `cottax` machinery entirely, producing a program equivalent to a manual ordering and ensuring that the runtime is spent entirely within the models and their (possibly coupled) solves. JAX’s automatic differentiation can be used over the entire dependency graph, including over (custom) solvers using implicit differentiation. Non-JAX functions (e.g. legacy models) can be wrapped, with finite differences as a backup when derivatives (from automatic differentiation) are not available (e.g. a meshing step).

To demonstrate `cottax`, we apply it to the PROCESS fusion systems code [2, 3]. PROCESS has over 140 different models with complex interdependencies and has different configurations that share less than half of their models, have different parametrisations, and have different problem formulations. Therefore, it provides a compelling test case for requirements 1 and 2. Since the models themselves are mostly fast scalar arithmetic, it also provides a test for the execution speed of the `cottax` graph machinery. First, we apply the automated coordination to seven different PROCESS configurations, showing how multiple MDAO architectures can be automatically assigned and run in all configurations, addressing requirements 1 and 2. Moreover, the results motivate requirement 3: no single MDAO architecture is best in all cases. Second, to investigate requirements 4 and 5, we profile the `cottax` JAX-based execution for these seven configurations. Automatic and implicit differentiation (including through nested solves) is used for the required Jacobians in all configurations. The timing results show two to three orders of magnitude less model time (i.e. not including driver computations) in `cottax` compared to base PROCESS, and show that removing orchestration overhead (by compiling the `cottax` graph) results in a 40\(\times\) speedup in a stellarator configuration.

Then, in Section III, the dependency graph, visualisations of it, conditional nodes and nesting edges, the workflow for getting to an executable graph, and automated MDAO architecture recipes are introduced. The `cottax` implementation is discussed in Section IV. In Section V, we apply it to the PROCESS systems code [2, 3], obtaining the dependency graph, sequencing it, and solving it with varying architectures. Finally, a discussion and conclusions are given in Sections VI and VII.

## II. STATE OF THE ART

Complex dependencies are often modelled as graphs, giving rise to classic systems-engineering diagrams such as the _N_<sup>2</sup> [31, 32] or Design Structure Matrix [33, 34], allowing for analysis such as clustering or minimal cycles. The dependencies between models in integrated design codes can be similarly encoded and visualised as a graph. Typically, this is done with an extended Design Structure Matrix that reveals the computational structure [35]. In fact, depending on the implementation approach such a dependency graph can be directly derived from the software [8, 36].

Aside from analysis of existing codes, graphs can also be used to formulate MDAO problems [28]. This allows sequencing algorithms such as Tarjan [29] to be used to automatically create a model order and isolate so-called strongly connected components. In essence, this is a reordering of computational tasks that can be related to computational optimisation approaches as used in compilers, where computational graphs allow the program to be aggressively optimised [37]. For example, the statically known graph enables efficient ordering and dead-code elimination. Similar strategies have been applied to dependency graphs at a higher abstraction level such as individual disciplines in an MDAO context [38-40]. Several state-of-the-art frameworks integrate such approaches in different ways.

OpenMDAO [8, 41] is an established multidisciplinary framework, providing efficient derivatives of large-scale analysis using the MAUD architecture [42]. It focuses on monolithic architectures that may contain nested solvers, but does not provide the desired flexibility to easily (re)configure a large collection of models. It can automatically find model execution order within a model Group, but does not facilitate easy (re)configuration of those Groups when cyclic model dependencies are changing. Reconfiguration of the MDAO architecture requires manually recomposing the Groups. OpenMDAO supports MPI [43] and PETSc [44] to parallelise model groups and large linear solvers (such as required for MAUD Jacobian computation), and JAX-based components can be included; however, the orchestration layer remains in Python. We prefer to avoid the overhead with a JAX-native orchestration layer for cases with many small, fast models.

GEMSEO [25, 45] is a Python-based engine for multidisciplinary design exploration and optimisation that supports both distributed and monolithic architectures. Though GEMSEO can automatically order models and assign a preconfigured MDAO architecture, it does not support easily modifying which solver converges which variables and models. Similar to OpenMDAO, the nesting in the MDAO architecture needs to be hard-coded for the specific application. In terms of gradient handling, GEMSEO allows both direct and adjoint propagation using coupled adjoint theory [46]. With a plugin [47] (a chain of) JAX-based disciplines can be supported, but the framework itself is not JAX-native so some overhead remains.
