Moving forward, we will use \(X=(P_1,\emptyset),\dots,(P_a,m_a),(P_i,b)\) to reference the relevant source chain associated with (_x_<sub>1</sub>_,y_<sub>1</sub>), and _I_<sub>1</sub> to be the relevant compatible input assignment. We define _Y_ and _I_<sub>2</sub> analogously but now with respect to (_x_<sub>2</sub>_,y_<sub>2</sub>). Recall that by construction _P_<sub>1</sub> is assigned the same bit _b_<sub>1</sub> in _I_<sub>1</sub> and _I_<sub>2</sub>.

We consider two cases concerning the players that shop up in chains _X_ and _Y_:

**Case 1:** \(players(X)\neq players(Y)\).

By definition: both (_x_<sub>1</sub>_,y_<sub>1</sub>) and (_x_<sub>2</sub>_,y_<sub>2</sub>) are valid value pairs. It follows that both are bivalent, meaning that the input bits of the players that have sent or receive bits so far are not sufficient to determine the value of the function. A straightforward contradiction argument establishes that no player in either chain can output until the chain extends further, as if any player outputs 0, the bits of the players not in the chain can be set to ! to make that answer incorrect, and if any player outputs 1, the remaining bits can be set to 0. Therefore, when we get to step (_P<sub>i</sub>,b_) in both chains, the output has not yet been determined.

Because \(players(X)\neq players(Y)\), there must be a player _P<sub>j</sub>_ in one set but not the other. Without loss of generality, say _P<sub>j</sub>_ is only in _players(X_). Fix any possible extension _Y,Z_ of _Y_ (where "possible" means there is an input assignment to the players in _Z_ such that when combined with the fixed assignments for players in _Y_ , _Y,Z_ describes the steps of the resulting execution).

The key observation is that it must be the case that \(P_j\notin players(Z)\). This follows because if _Z_ extends _Y_ then it also extends _X_, as both _X_ and _Y_ end with the same step: _P<sub>i</sub>_ receiving _b_. However, _X,Y_ cannot occur because it features _P<sub>j</sub>_ both in _X_ and _Z_, meaning that this chain would require the same non-initiator player<sup>4</sup> _P<sub>j</sub>_ to receive 2 bits, which it cannot given our assumption of a local complexity of 1.

This observation creates an obstacle for the correctness of our protocol. We have just established that every way we can extend _Y_ must omit _P<sub>j</sub>_. Consider the extension _Z_ that occurs when we fix the input bits of all players that are not in _players(X_) and not _P<sub>j</sub>_, such that the total number of 1 bits is _k_-1. The execution corresponding to _Y,Z_ must eventually output. It does so, however, without _P<sub>j</sub>_ sending a bit. If this execution outputs 1, then it is incorrect in the case where _P<sub>j</sub>_ has bit 0, and if it outputs 0, then it is incorrect in the case where _P<sub>j</sub>_ has bit 1.

**Case 2:** _players(X)=players(Y_):

If _players(X)=players(Y_) then it follows that _y_<sub>1</sub>=_y_<sub>2</sub>. Because \((x_1,y_1)\neq(x_2,y_2)\), it also follows that \(x_1\neq x_2\). That is, the number of 1 bits encountered before _P<sub>i</sub>_ receives _b_ is different in _X_ versus _Y_ . Player _P<sub>i</sub>_, of course, receives the same bit in both cases, so it must proceed without knowing if the count is _x_<sub>1</sub> or _x_<sub>2</sub>. The only player in these chains that can possibly receive another bit is the common initiator _P_<sub>1</sub>, as only initiators send a bit before receiving any bit. Since this initiator has the same input bit in both _X_ and _Y_ (here is why it was important that we earlier identified two chains that satisfied this property), our protocol must eventually output without ever learning the true count of 1 bits in the prefix leading up to _P<sub>i</sub>_’s step.

To formalize this intuitive trouble, assume without loss of generality that _x_<sub>1</sub>_\>x_<sub>2</sub>. Because (_x_<sub>1</sub>_,y_<sub>1</sub>) is valid, we know _x_<sub>1</sub>_\<k_. Consider the extension _X,Z_ that occurs when we set exactly _k-x_<sub>1</sub> of the players _outside players(X_) to have input bit 1. The input assignment corresponding to _X,Z_ includes exactly _k_1 bits, therefore some step in _Z_ must correspond to a player outputting 1.

If we consider this _same_ input assignment for the players outside of _players(X)=players(Y_), we will get the _same_ extension _Y,Z_, as the last step in _Y_ is the same as the last step in _Z_. The set _players(Z_) is disjoint from the set _players(Y_) with the possible exception of _P_<sub>1</sub>, as it is possible that the initiator ends the chain it started. By definition, however, all players in _players(Z_) have the same input bit in the assignments corresponding to _X,Z_ and _Y,Z_ (recall, we selected _X_ and _Y_ specifically because their corresponding assignments give _P_<sub>1</sub> the same bit), and they receive and send the same bits in both, so the player in _Z_ that outputs 1 in the execution corresponding to _X,Z_ also outputs 1 in the execution corresponding to _Y,Z_. This latter output, however, is incorrect, as the number of 1 bits n the corresponding input assignment is strictly less than _k_.
