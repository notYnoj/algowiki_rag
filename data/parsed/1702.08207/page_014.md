In the statement of Algorithm 4.1, we recall that, given a tree _T_=(_V,E,w_), tree \(T'=(V,E,w')\) is the tree with weights rounded up to the nearest multiple of the length of a slot (see Equation (4.1)).

The subsequent steps taken in procedure BuildStrategy can be informally sketched as follows. The input tree \(T'\) is processed in a bottom-up manner and hence, for an input vertex _v_, the recursive calls for its children _v_<sub>1</sub>_,...,v<sub>l</sub>_ are first made, providing schedule assignments for the children (see lines 3-4). Then, the rest of the pseudocode is responsible for using these schedule assignments to obtain all valid schedule assignments for _v_. Lines 10-14 merge the schedules of the children in such a way that a set \(\hat{S}_i^*\), \(i\in\{1,\dots,l\}\), contains all schedule assignments computed on the basis of the schedules for the children _v_<sub>1</sub>_,...,v<sub>i</sub>_. Thus, the set \(\hat{S}_l^*\) is the final product of this part of the procedure and is used in the remaining part. Note that a schedule assignment in \(\hat{S}_l^*\) may not be valid since a query to _v_ is not accommodated in it -- the rest of the pseudocode is responsible for taking each schedule \(s\in\hat{S}_l^*\) and inserting a query to _v_ into _s_. More precisely, the subroutine InsertVertex is used to place the query to _v_ at all possible time points (depending whether _v_ is heavy or light). We note that the subroutine MergeSchedules, for each schedule _s_ it produces, sets a Boolean ‘flag’ _s.must\_contain\_v_ that whenever equals _false_, indicates that querying _v_ is not necessary in _s_ to obtain a valid schedule for _v_ (this happens if _s_ queries all children of _v_). A detailed analysis of procedure BuildStrategy can be found in the proof of Lemma 4.6.

**Lemma 4.6.** _For fixed constants_ \(L,c\in\mathbb{N}\)_, calling procedure_ \(\text{BuildStrategy}(r(T),\omega)\)_, where r(T_) _is the root of the tree, determines if there exists a tuple_ \((s_v,t_v)_{v\in V}\) _which satisfies constraints_ (4.4), (4.5)_, and_ (4.6)_, or returns an empty set otherwise._

_Proof._ The formulation of procedure BuildStrategy directly enforces that the constraints (4.4), (4.5), and (4.6) are fulfilled at each level of the tree, in a bottom-up manner.

For each vertex \(v\in V\) , we show by induction on the tree size that upon termination of procedure \(\text{BuildStrategy}(v,\omega)\), the returned variable \(\hat{\mathcal{S}}[v]\) is the set of all _minimal_ schedules \((s_v,t_v)\in\hat{\mathcal{S}}[v]\) which can be extended within the subtree _T<sub>v</sub>_ to a data structure \((s_u,t_u)_{u\in V(T_v)}\), for some \((s_u,t_u)\in\hat{\mathcal{S}}[u]\), \(u\in V(T_v)\), in such a way that the conditions (4.4), (4.5), and (4.6) hold within subtree _T<sub>v</sub>_. Here, minimality of a schedule is a trivial technical assumption, understood in the sense of the following very restrictive partial order: we say \((s_v,t_v)\le(s'_v,t'_v)\) if \(s_v[p]\le s'_v[p]\) for all \(0\le p\le L-1\) and \(t_v=t'_v\). (In the pseudocode, rather than write (_s<sub>v</sub>,t<sub>v</sub>_) as a pair variable, we include _t<sub>v</sub>_ within the structure _s<sub>v</sub>_ as its special field _s<sub>v</sub>.t<sub>v</sub>_.)

The algorithm proceeds to merge together exhaustively all possible choices of schedules \((s_{v_i},t_{v_i})\in\hat{\mathcal{S}}[v_i]\) of all children _v<sub>i</sub>_ of _v_, \(1\le i\le l\). The merge is performed by computing, for any fixed choice \((s_{v_i},t_{v_i})_{1\le i\le l}\), the combined load of each box in the resultant schedule _s_:

\(s[p]\leftarrow\sum_{i=1}^ls_{v_i}[p],\) (4.7)

where, as a technicality, we also put \(s[p]\leftarrow+\infty\) whenever we obtain excessive load in a box (_s_\[_p_\]_\>_1), as to avoid inflating the size of the state space and consequently, the running time of the algorithm. In Algorithm 4.1, the computation of _s_\[_p_\] through the sum (4.7) proceeds by a processing of successive children _v<sub>i</sub>_, \(1\le i\le l\), so that a schedule _s_ stored in the data structure \(\hat{\mathcal{S}}_i^*\) represents \(s[p]=\sum_{i=1}^ls_{v_j}[p]\). The summation of load is performed within the subroutine MergeSchedules, which merges a schedule \(s_{orig}\in\hat{\mathcal{S}}_{i-1}^*\) with a schedule \(s_{add}\in\hat{\mathcal{S}}[v_i]\) to obtain the new schedule \(s\in\hat{\mathcal{S}}_i^*\).
